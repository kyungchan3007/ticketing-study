그때 놓쳤던 부분, 주의 깊게 보지 않았던 부분은 무엇이었는지,
왜 생산성이 떨어졌는지 다시 확인해보고
에이전트를 제어하는 방법을 하나씩 개선해 나가고 싶어서 프로젝트를 시작하게 되었습니다!

## 🧭 이 프로젝트에서 해보려는 것

- **복기**: 현업에서 에이전트 팀을 어떻게 나눴고, 어떤 규칙으로 일을 시켰는지 다시 짚어보려고 합니다.
- **확인**: 같은 방식으로 다시 구현해보면서, 그때 놓쳤던 부분과 생산성이 떨어진 원인을 찾아보려고 합니다.
- **개선**: Anthropic 문서와 에이전트 설계에 관한 여러 문서를 참고해서, 에이전트를 제어하는 방법을 바꿔보고 전후를 비교해보려고 합니다!

## 🛠 진행 방법

인프런 강의 「실리콘밸리 개발자와 함께 보는 티켓 예매 시스템 디자인」의 설계 방향과 순서를 기준으로
콘서트 좌석 예매 서비스를 처음부터 다시 만들어보려고 합니다.
다만 강의를 그대로 따라 하지 않고, 현업에서 했던 방식을 접목해보려고 합니다!

### 강의와 다른 부분들
- **프론트엔드**: 강의는 백엔드 설계가 중심이라 화면은 마지막에 간단히 붙이는데, 저는 프론트엔드까지 다뤄보려고 합니다! 티켓 예매 서비스에 잘 맞는 아키텍처를 찾아보고, 디자인 시스템과 모듈을 나누는 방법까지 함께 적용해보려고 합니다.
- **프롬프트**: 강의 프롬프트를 그대로 쓰지 않고, 현업에서 필요했던 조건(범위, 완료 기준, 하지 말아야 할 것)을 더해서 써보려고 합니다.
- **규칙 문서**: 에이전트가 매번 읽는 규칙은 꼭 필요한 것만 짧게 두고, 가끔 필요한 문서는 위치만 남겨서 필요할 때 꺼내 보게 해보려고 합니다.
- **보호 장치**: 꼭 지켜야 하는 규칙은 부탁(규칙 문서)이 아니라 강제(훅, 검사기)로 막을 수 있는지 확인해보려고 합니다.
- **작업 범위**: 에이전트가 부탁받은 범위만 하고 보고한 뒤 멈추게 해서, 다음 단계는 사람이 정하는 흐름을 만들어보려고 합니다.

### 기록 방법
- 섹션마다 이슈를 하나 만들고, 단계별 작업은 서브 이슈로 나눠서 기록해보려고 합니다.
- 에이전트에게 준 프롬프트와 결과, 스크린샷은 이슈 댓글로 남기려고 합니다.
- 참고한 문서는 각 이슈에 링크로 남겨두려고 합니다.
- 섹션이 끝날 때마다 태그(`s1-done` 등)를 찍어서, 단계별로 무엇이 달라졌는지 비교해보려고 합니다!

## 🤖 에이전트 팀

사람이 무엇을 만들지 정하고 결과를 검수하며, 에이전트는 네 가지 역할로 나눠보려고 합니다.

| 역할 | 맡을 일 |
| --- | --- |
| lead | 계획을 세우고 일을 나누고 결과를 통합 |
| test | 구현보다 먼저 테스트를 작성 |
| server | 테스트를 통과하도록 서버를 구현 |
| review | 구현 결과를 독립적으로 검토 |

에이전트 하나에 모든 일을 맡기면 코드 대신 테스트를 고쳐서 통과시킬 수 있다고 생각합니다.
역할별 수정 범위를 나누고, 훅과 테스트 파일 검사로 이 문제를 막을 수 있는지 확인해보려고 합니다!

```
요구 정의 → 테스트 작성(FAIL) → 구현(PASS) → 리뷰
```

## 🎯 왜 티켓 예매 서비스인가

티켓 예매는 도메인일 뿐이고, 여기서 생기는 문제는 대부분의 웹·앱 서비스에서 똑같이 생긴다고 생각합니다.
선착순 쿠폰, 한정 수량 상품 주문, 숙소·병원 예약, 결제처럼 **여러 사용자가 같은 자원을 동시에 가지려는 상황**은 어디에나 있습니다.
티켓 예매는 이런 문제가 한 화면 안에 모두 모여 있고, 실패했을 때 결과가 분명하게 드러나서 공부하기 좋은 주제라고 생각했습니다!

### 백엔드에서 마주치는 문제
- **동시성**: 같은 좌석에 요청이 동시에 들어왔을 때 한 명만 성공하게 하려면 어떻게 해야 하는지
- **멱등성**: 네트워크 문제로 같은 요청이 여러 번 와도 결과가 한 번만 반영되게 하려면 어떻게 해야 하는지
- **상태 전이와 트랜잭션**: 빈 좌석 → 홀드 → 판매 상태가 중간에 꼬이지 않게 하려면 어떻게 해야 하는지
- **트래픽 급증**: 순간적으로 몰리는 요청을 어떻게 나누고, 막고, 줄 세워야 하는지

### 프론트엔드에서 마주치는 문제
- **중복 요청**: 사용자가 버튼을 여러 번 눌러도 요청이 한 번만 가게 하려면 어떻게 해야 하는지
- **낡은 화면 상태**: 다른 사람이 먼저 잡은 좌석을 화면에 어떻게 빨리 반영해야 하는지
- **실패와 재시도**: 서버가 거절하거나 응답이 늦을 때 사용자에게 무엇을 보여주고, 다시 보내도 안전하게 하려면 어떻게 해야 하는지
- **서버와의 계약**: 화면과 서버가 같은 규칙을 보고 있다는 걸 어떻게 보장해야 하는지

이 모든 문제를 관통하는 기준은 하나입니다.

> **좌석 하나는 한 번만 팔려야 한다.**

한 좌석에 500명이 동시에 요청을 보냈을 때 정확히 1명만 성공하고,
나머지 499명은 이미 잡힌 좌석이라는 응답을 받으며,
서버 오류는 없는지 직접 실행해서 확인해보려고 합니다!

## 🔍 알아보려는 것

- **백엔드**: 트래픽 계산, 동시성 제어, 홀드 만료와 모의 결제, Nginx 요청 분산과 제한, Redis 캐시와 가상 대기열, Kafka 알림, 쿠버네티스 부하 테스트
- **프론트엔드**: 아키텍처, 디자인 시스템, 모듈 구조, API 계약에서 만든 타입으로 화면 붙이기
- **전체**: 공부한 내용을 면접처럼 처음부터 다시 설계하며 설명해보려고 합니다!

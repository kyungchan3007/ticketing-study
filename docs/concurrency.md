# 동시성 확인

목표: 같은 좌석에 여러 명이 동시에 몰려도 정확히 한 명만 성공하고, 서버 오류(5xx)는 없다. 이것을 실제 서버와 PostgreSQL로 돌려 확인한다.

## 1. 테스트

`tests/concurrency/test_concurrency.py`. 테스트가 `uvicorn backend.main:app --workers 4`를 별도 프로세스로 띄우고, 테스트 DB(`tkt_test`)를 쓴다. 요청은 미리 만들어 두고 한꺼번에 출발시킨다(httpx AsyncClient).

| 테스트 | 요청 | 기대 |
|---|---|---|
| `test_concurrent_hold_500_users_one_seat` | 서로 다른 사용자 500명이 같은 좌석을 동시에 홀드 | 201 1건, 409 `SEAT_ALREADY_HELD` 499건, 5xx 0건 |
| `test_concurrent_confirm_20_same_hold` | `u1`이 같은 hold_id로 동시에 확정 20번 | 200 1건, 409 19건, 5xx 0건, `bookings`의 그 좌석 줄 1개 |

- 확정의 성공 코드는 계약(`docs/openapi.yaml`)의 200이다.
- 한 번 통과는 운일 수 있어서, `uv run pytest tests/concurrency`를 3번 연속 돌려 모두 통과해야 통과로 본다.

## 2. 찾은 결함: DB 연결 한도

처음 실행에서 홀드 500건 테스트가 실패했다. 성공(201)은 매번 1건이었지만 `500 INTERNAL_ERROR`가 148~261건 나왔다.

- 원인: `psycopg.OperationalError: FATAL: sorry, too many clients already`. 워커 4개 × 연결 풀(`pool_size` 10 + `max_overflow` 20 = 30) = 최대 120 연결이 PostgreSQL `max_connections` 100을 넘었다.
- 수정(`backend/db.py`): 워커당 연결 풀을 `pool_size` 10 + `max_overflow` 5 = 15로 줄였다. 4 × 15 = 60이라 한도 안이고, 남는 40은 테스트·마이그레이션 여유다. 한도를 넘는 요청은 풀에서 연결을 기다린다(`pool_timeout` 30초).
- 주의: 전체 연결 수는 `서버 인스턴스 수 × 워커 수 × 15`다. 인스턴스나 워커를 늘리면 이 값이 `max_connections` 이하인지 다시 맞춰야 한다(T-18 리뷰 #2).
- 다루지 않은 경우: 연결 15개가 모두 잠금 대기에 묶여 다음 요청이 `pool_timeout`(30초)을 넘기면 지금은 `500 INTERNAL_ERROR`가 된다. 이 응답은 그대로 500으로 두기로 했다(PRD 10절 Q15).

## 3. 테스트가 겹침을 잡는지 확인 (잠금 제거 실험)

`lock_seat`의 `with_for_update()`를 잠깐 빼고 돌렸다(되돌린 뒤 흔적 없음 확인).

| 테스트 | 잠금 없음 | 잠금 있음 |
|---|---|---|
| 홀드 500건 | **FAIL**: 201 4건, 409 496건 (이중 홀드) | PASS |
| 확정 20건 | **FAIL**: 200 1건, 500 19건 (`uq_bookings_seat` UNIQUE 위반) | PASS |

잠금이 없으면 테스트가 실제로 실패한다. 확정 쪽은 UNIQUE 제약이 이중 판매를 막았지만, 그 대가로 5xx가 났다.

## 4. 홀드 방식 비교

두 방식을 경우 3가지로 쟀다. 값은 10라운드의 중앙값이고 괄호는 범위다. 201·409·5xx 수는 두 방식 모두 매 라운드 같았다.

- A. `SELECT … FOR UPDATE`로 좌석 행을 잠그고 판단·변경 (현재, 기존 테스트 전체 통과)
- B. 조건부 `UPDATE … WHERE (홀드 가능) RETURNING` 한 번 (기존 테스트 1건 실패, 아래 "남긴 방식" 1번)

### 같은 좌석에 서로 다른 사용자 500명
| 방식 | p50(ms) | p95(ms) | 201 | 409 | 5xx |
|---|---:|---:|---:|---:|---:|
| A | 321 (307~356) | 428 (407~468) | 1 | 499 | 0 |
| B | 354 (321~502) | 394 (346~527) | 1 | 499 | 0 |

### 경합 없음: 서로 다른 좌석 100석에 100명(좌석당 1명)
| 방식 | p50(ms) | p95(ms) | 201 | 409 | 5xx |
|---|---:|---:|---:|---:|---:|
| A | 80 (74~94) | 91 (84~104) | 100 | 0 | 0 |
| B | 76 (70~88) | 85 (82~95) | 100 | 0 | 0 |

### 100석에 500명이 흩어져서(좌석당 5명, 사용자 i → 좌석 i % 100)
| 방식 | p50(ms) | p95(ms) | 201 | 409 | 5xx |
|---|---:|---:|---:|---:|---:|
| A | 387 (349~426) | 422 (379~460) | 100 | 400 | 0 |
| B | 368 (340~403) | 402 (382~440) | 100 | 400 | 0 |

- 세 경우 모두 두 방식의 범위가 겹친다. 경합이 없을 때 B가 약 4~6ms 빠르고, 경합이 있을 때는 p50은 A, p95는 B가 조금 낮거나(같은 좌석) 둘 다 B가 조금 낮다(흩어짐). 어느 쪽도 확실히 빠르다고 할 차이가 아니다.
- 요청 수가 같으면(500건) 같은 좌석과 흩어짐의 시간이 비슷하다. 시간 대부분이 좌석 잠금 대기가 아니라 HTTP 처리와 연결 풀 대기(워커당 15개)라는 뜻이다.
- 5장 처음 측정(같은 좌석 500명만, `tkt_test`, server 임시 스크립트)은 A p50 310·p95 418, B p50 342·p95 374로 이번과 같은 흐름이었다.

### 처리량과 응답 시간 (현재 방식 A)

두 숫자는 서로 다른 것을 잰다.

- **처리량:** 서버가 1초에 끝내는 요청 수. 배치 전체 시간(모든 요청이 한꺼번에 출발한 순간부터 마지막 응답이 도착한 순간까지)을 재고, `요청 수 ÷ 배치 전체 시간`으로 구한다. 서버를 몇 대 둘지 정할 때 쓴다.
- **응답 시간:** 요청 하나가 출발해서 응답을 받기까지 걸린 시간(p50·p95). 사용자 한 명이 기다리는 시간이다.
- **섞으면 안 되는 이유:** 요청이 동시에 처리되므로 처리량은 `1 ÷ 응답 시간`이 아니다. 아래 같은 좌석 500명에서 p50은 309ms이지만, 이것으로 "1초에 약 3건"이라고 계산하면 실제 처리량(약 1,020건/초)과 300배 넘게 차이 난다. 반대로 처리량이 높아도 몰릴 때는 사용자 한 명의 응답 시간이 길어질 수 있다(요청이 연결 풀에서 기다리므로).

`uv run python scripts/bench_hold.py --runs 10`, `tkt_server`, 10라운드 중앙값(괄호는 범위).

| 경우 | 요청 | 배치 전체(ms) | 처리량(건/초) | 응답 p50(ms) | 응답 p95(ms) | 201 / 409 / 5xx |
|---|---:|---:|---:|---:|---:|---|
| 같은 좌석에 서로 다른 사용자 500명 | 500 | 490 (481~533) | 1,020 (939~1,040) | 309 (294~353) | 409 (396~454) | 1 / 499 / 0 |
| 경합 없음: 서로 다른 좌석 100석에 100명 | 100 | 96 (88~118) | 1,038 (850~1,135) | 80 (66~87) | 90 (77~105) | 100 / 0 / 0 |
| 100석에 500명이 흩어져서(좌석당 5명) | 500 | 426 (400~478) | 1,174 (1,046~1,250) | 338 (307~421) | 373 (351~452) | 100 / 400 / 0 |

- 경우가 달라도 처리량은 초당 약 1,000~1,200건으로 비슷하다. 같은 좌석에 몰려도 처리량이 크게 줄지 않는다. 경합 없음은 요청이 100건이라 배치가 짧아(약 0.1초) 범위가 넓다.
- 이번 응답 시간은 위 A·B 비교 때(같은 날 다른 실행)와 범위가 겹친다.
- **`docs/capacity.md`와 비교:** 홀드 최대 400건/초, 예매 API(조회·홀드·결제) 합계 880건/초는 이 서버 한 대의 홀드 처리량(약 1,000~1,200건/초) 안이지만, API 합계 최대 약 21.5만 건/초(대부분 순번 확인 폴링)는 약 200배다. 폴링은 G8대로 이 서버가 아닌 대기열 쪽에서 받아야 한다.
- **한계:** 서버 한 대(uvicorn 워커 4개), 클라이언트·서버·PostgreSQL이 모두 같은 노트북에 있는 로컬 측정이다. 500건을 한 번에 보내는 짧은 몰림이고, 몇 분씩 이어지는 부하가 아니다. 홀드만 쟀고 좌석 조회·결제는 재지 않았다. 데이터도 좌석 100석뿐이다. 그래서 이 숫자는 실제 서버 대수를 정하는 값(`docs/capacity.md` 5절 [실측 필요])이 아니라 크기를 가늠하는 값이다.

### 다시 재는 방법
```bash
uv run python scripts/bench_hold.py --runs 10            # 세 경우, 경우마다 10라운드(워밍업 1회 별도). 처리량·응답 시간을 함께 출력
uv run python scripts/bench_hold.py --runs 20 --cases same,scatter
```
- 서버(uvicorn 워커 4개)를 띄우고 `tkt_server`의 데이터를 라운드마다 지우고 다시 넣는다. `tkt_test`를 주면 거부한다. 테스트와 같은 시각에 돌려도 테스트 DB는 건드리지 않지만, 같은 기기라 숫자가 흔들린다.
- 요청마다 새 연결로 보낸다. 연결을 미리 열어 두고 다시 쓰면 응답 시간이 4~5배로 늘었다(같은 좌석 500명 p50 약 1,450ms). 미리 연 연결이 일부 워커에 몰리는 것으로 보이지만 확인하지 않았다. 실제 사용자는 각자 연결을 연다.
- 도구는 현재 저장소의 서버(A)를 잰다. B는 server가 저장소 밖 복사본에서 다시 만들어 `--app-dir`로 한 번 쟀고 저장소에는 넣지 않았다(사람 결정).

### 남긴 방식: A (FOR UPDATE)
1. **정확성.** B는 기존 테스트 `test_us03_ac03_3_expiry_judged_after_seat_lock`에서 실패했다. B는 시각을 UPDATE 전에 읽어야 해서, 행 잠금을 기다리는 동안 지난 시간이 만료 판단에 들어가지 않는다(T-03 리뷰 #1, `docs/tasks/api-harness.md` 2절).
2. **단순함.** B를 정확하게 만들려면 만료 시각을 `seats` 행에 복사하는 컬럼과 마이그레이션이 필요하다. 만료 시각을 `holds`에서 하위 질의로 읽으면, PostgreSQL READ COMMITTED에서 막혔던 행을 다시 확인할 때 다른 트랜잭션이 막 넣은 홀드 행이 보이지 않아 이중 홀드가 될 수 있다.
3. **속도.** 세 경우 모두 차이가 작고 범위가 겹친다. B가 빠르다고 할 근거가 없다.

## 5. 예매 표 UNIQUE 제약

`bookings`에는 처음 마이그레이션(`backend/migrations/versions/0001_initial.py`)부터 `uq_bookings_seat` UNIQUE (performance_id, seat_id)가 있다. 테스트 DB에서 `\d bookings`로 확인했다. 새 마이그레이션은 만들지 않았다.

## 6. 리뷰(T-18) 결과와 처리

review 결론: 홀드와 확정은 좌석 행 하나를 FOR UPDATE로 같은 순서로 잠그고, 시각도 잠금 뒤에 한 번 읽는다. 이중 판매나 좌석 사이 교착 경로는 찾지 못했다. 이 문서의 A·B 설명은 코드와 맞는다.

| 번호 | 심각도 | 지적 | 처리 |
|---|---|---|---|
| 1 | 중간 | 좌석맵이 좌석과 홀드를 서로 다른 SQL 문으로 잠금 없이 읽어, 그 사이 확정·재홀드가 커밋되면 이전 상태를 보일 수 있다 | **바꾸지 않음.** 홀드 행은 만들어진 뒤 바뀌지 않으므로, 응답은 좌석을 읽은 순간의 상태와 같다. 응답이 나간 직후 상태가 바뀌는 것과 같은 정도의 지연이고, 한 응답 안에서 서로 맞지 않는 상태가 섞이지는 않는다. 판매 판단은 좌석맵이 아니라 잠금을 잡은 홀드·확정이 한다 |
| 2 | 중간 | 연결 한도 식이 인스턴스 수를 빠뜨림. 풀 대기가 30초를 넘으면 500 | 식을 고침(2절, `backend/db.py` 주석). 과부하 응답은 500 그대로(PRD 10절 Q15 결정) |
| 3 | 낮음 | 실제 서버 테스트가 다루지 않는 경쟁: 만료 경계에서 이전 홀드 확정과 재홀드, 다른 사용자의 같은 hold_id 동시 확정, 좌석맵과 상태 변경 | **이번에 테스트 추가 안 함.** 다른 사용자의 확정은 응답이 열린 질문 Q3이다. 만료 경계는 실제 서버(다른 프로세스)에서 시각을 바꿀 방법이 없고 테스트 전용 경로는 만들지 않는다. 같은 판단(잠금 뒤 시각·`current_hold_id` 확인)은 `tests/api/`의 `..._expiry_judged_after_seat_lock`, `test_us04_ac04_6_hold_then_confirm_race`가 확인한다. 좌석맵은 1번과 같다 |

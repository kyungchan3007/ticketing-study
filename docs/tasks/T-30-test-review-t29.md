# T-30 (test) T-29 리뷰 지적 반영 테스트

## 배경 (review T-29, 판정 미해결, 지적 2건 모두 중간)
1. `Idempotency-Key` 검사가 홀드 조회 뒤에 있어서, 키 없는 요청이 홀드가 있느냐 없느냐(또는 DB 상태)에 따라 404나 500이 된다. 계약(`docs/openapi.yaml` confirmBooking 400)은 키 없음을 400 `VALIDATION_ERROR`로 정했다. lead 결정: 키 검사는 `X-User-Id` 검사처럼 **요청 형식 단계에서 가장 먼저** 한다(401 → 400 → 그다음 홀드 조회). server는 `tests/api/test_internal_error.py`의 확정 DB 장애 테스트가 키 없이 500을 기대해서 검사 순서를 뒤로 미뤘다.
2. 같은 사용자가 **서로 다른 좌석**의 홀드에 **같은 키**를 동시에 쓰는 경우를 테스트하지 않았다. 좌석 잠금이 서로 달라서 이 경우는 `uq_bookings_user_key` 제약에 기댄다.

## 할 일
1. `tests/api/test_internal_error.py`: 확정 DB 장애 테스트가 `Idempotency-Key`를 보내게 고친다(그래야 키 검사와 상관없이 DB 장애 500을 본다). 기대값(500 `INTERNAL_ERROR`)은 그대로다.
2. 새 테스트(US-04 AC-04-12 묶음): 없는 `hold_id` + 키 없음 → 400 `VALIDATION_ERROR`. 지금 서버에서는 404라 **실패(FAIL)** 해야 한다. 이름은 `test_us04_ac04_12_...`.
3. 새 테스트(US-04 AC-04-13 묶음): `u1`이 `A1`·`A2`를 홀드한 뒤 같은 키 `k1`로 두 예매 요청을 동시에 출발시킨다. 기대: 2xx `PENDING` 정확히 1건, 409 `IDEMPOTENCY_KEY_REUSED` 1건, 5xx 0건, `u1`의 `k1` 예매 줄 1개. 기존 동시 테스트처럼 같은 테스트 안에서 여러 번 반복한다. 지금 서버에서 통과(PASS)해도 된다(회귀 방지). 대신 실제로 두 요청이 겹치는지(둘 다 사전 조회를 통과하는 경로)를 확인할 방법이 있으면 적는다.
4. 바뀌지 않은 테스트의 기대값은 그대로 둔다. `tests/`만 수정한다. 커밋하지 않는다.

# T-35 (review) 긴 Idempotency-Key 500 결함 수정 검토

읽기만 한다. 결과는 자기 화면에 남긴다(lead가 transcript로 읽는다). 재현이 필요하면 재현 명령과 기대 결과를 적는다.

## 반영 내용
- 결함(사람 재현): 무작위 3000자 키 → 500, 로그 `index row size 3016 exceeds btree version 4 maximum 2704 for index "uq_bookings_user_key"`.
- 계약(lead): 키 1~255자, 넘으면 400 `VALIDATION_ERROR`(`docs/openapi.yaml` IdempotencyKey maxLength 255, PRD 5절, US-04 AC-04-14).
- 테스트(T-33): `tests/api/test_us04_confirm_booking.py`의 `test_us04_ac04_14_*`(256자·무작위 3000자 400, 255자 2xx, 계약). 고치기 전 256자는 200, 3000자는 500으로 FAIL. 같은 커밋 단위로 빠진 확인 3가지(다중 좌석 동시 콜백, 다른 사용자 같은 키, 실패 뒤 새 키의 FAILED 1·PENDING 1)도 추가됐다.
- 구현(T-34): `backend/main.py` `check_idempotency_key`에 255자(문자 수) 검사. DB 제한(CHECK·마이그레이션)은 넣지 않음 — API가 막으면 255자 × 최대 4바이트 = 1020바이트라 btree 한도에 닿지 않고, 이 표에 쓰는 경로는 API 하나뿐이라는 이유.
- 참고: `tkt_server`에 이미 5000자 키 예매 1건(PENDING)이 있다(사람 시험으로 보임, 같은 글자 반복이라 압축돼 인덱스에 들어간 것으로 추정). 지우거나 바꾸지 않았다.
- 결과(lead 확인): 127 passed, concurrency 3번 연속 통과(4 passed), 해시 14개 일치.

## 확인할 것
1. 400 검사가 모든 경로에서 DB에 닿기 전에 일어나는가(401 → 400 → 홀드 조회 순서 유지). 문자 수 기준이 btree 한도를 확실히 막는가(멀티바이트, 압축되지 않는 값).
2. DB 제한을 넣지 않은 판단이 맞는가. 이미 있는 긴 키(5000자)가 남아 있을 때 생길 수 있는 문제가 있는가.
3. 같은 키 → 같은 예매, 사용자별 키 분리 등 기존 판정을 바꾸지 않았는가.
4. 새 테스트(특히 무작위 키 선택, 다중 좌석 동시 콜백)가 의미 있는가.

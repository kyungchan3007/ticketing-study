# T-16 (test) 동시성 테스트 — 실제 서버·PostgreSQL

## 목표
"같은 좌석에 여러 명이 동시에 몰려도 정확히 한 명만 성공하고, 서버 오류는 없다"를 실제 실행으로 확인한다.

## 결과물
`tests/concurrency/`에 테스트 두 개(필요하면 conftest).

1. **동시 홀드 500건:** 서로 다른 사용자 500명이 같은 좌석(`holdSeat`)을 동시에 홀드한다.
   - 기대: 201 정확히 1건, 409 정확히 499건(code `SEAT_ALREADY_HELD`), 5xx 0건. 그 밖의 응답도 0건.
2. **같은 홀드로 동시 확정 20건:** `u1`이 홀드한 뒤, 같은 사용자·같은 hold_id로 `confirmBooking`을 동시에 20번 보낸다.
   - 기대: 성공 1건, 나머지 19건 409, 5xx 0건. DB `bookings`에 그 좌석 줄이 정확히 1개.
   - 성공 코드는 계약의 confirmBooking 성공 코드(현재 200)를 쓴다(지시문의 "201"은 성공 1건이라는 뜻으로 본다). 기존 `tests/api/conftest.py`처럼 계약에서 읽어도 된다.

## 실행 조건
- **실제 서버:** 테스트가 `uvicorn backend.main:app --workers 4`(빈 포트)를 별도 프로세스로 띄운다. `DATABASE_URL`은 테스트 DB(`TEST_DATABASE_URL`, 기본 `postgresql+psycopg://tkt:tkt@localhost:5432/tkt_test`). 준비가 될 때까지 기다리고, 끝나면 프로세스를 확실히 정리한다(워커까지).
- 데이터는 서버를 띄우기 전이나 각 테스트 전에 `backend.db.migrate`, `backend.seed.reset`으로 준비한다. 시각은 실제 시계를 쓴다(다른 프로세스라 monkeypatch가 닿지 않는다).
- **요청이 정말 겹치게:** 요청을 미리 만들어 두고 동시에 출발시킨다(스레드 Barrier 또는 asyncio.gather 등). 클라이언트 연결 수 제한이 500보다 작아서 요청이 줄 서지 않게 한다.
- macOS의 열린 파일 수 기본 제한(256)에 걸릴 수 있다. 필요하면 테스트 안에서 올린다.
- 가짜 저장소나 TestClient 하나로 돌리지 않는다. 테스트 전용 HTTP 경로는 쓰지 않는다.
- 같은 테스트를 **3번 연속** 돌려 모두 통과해야 통과로 본다. lead가 `uv run pytest tests/concurrency`를 3번 돌린다. 한 번 실행이 너무 오래 걸리지 않게 한다.
- DB에 연결할 수 없으면 건너뛰지 않고 실패한다(기존 규칙).

## 할 일
1. 위 두 테스트를 쓴다. `tests/`만 수정한다. 기존 테스트는 바꾸지 않는다.
2. 지금 서버로 `uv run pytest tests/concurrency`를 돌린다. 지금 서버는 이미 FOR UPDATE를 써서 통과할 수 있다. 통과해도 괜찮다. 겹침을 정말 잡는지는 server가 잠금을 잠깐 빼고 확인한다(T-17). 실패하면 실패 출력과 이유를 그대로 보고한다(테스트를 맞추려고 기대값을 바꾸지 않는다).
3. 응답 코드별 개수를 실패 메시지에 넣어서, 실패했을 때 무엇이 몇 건이었는지 바로 보이게 한다.

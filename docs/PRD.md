# PRD — 콘서트 좌석 예매 1차 범위(MVP)

## 1. 목표
사용자가 다음 흐름을 API로 끝까지 진행할 수 있다.

1. 공연 목록을 본다.
2. 공연 하나의 좌석맵(좌석별 상태)을 본다.
3. 좌석 하나를 5분 동안 잡는다(홀드).
4. 예매를 요청하면 결제 대기(PENDING) 예매가 생긴다.
5. 모의 결제사가 결과를 콜백으로 알려 주면 그때 예매가 끝난다(성공이면 좌석이 SOLD).

## 2. 핵심 원칙
- **좌석 하나는 한 번만 팔린다.** 같은 요청이 동시에 여러 번 와도 마찬가지다.
- **돈은 한 번만 반영된다.** 같은 예매 요청을 다시 보내도 예매는 하나이고, 같은 결제 콜백이 여러 번 와도 한 번만 반영된다.
- **시각은 서버 시각만 쓴다.** 만료 판단은 서버가 읽은 현재 시각(`backend/clock.py`)으로만 한다. 결제사가 보낸 시각은 쓰지 않는다.
- 좌석에 대한 홀드와 확정은 동시에 들어와도 위 원칙을 깨지 않아야 한다. 이것이 이번 범위에서 가장 중요한 검증 대상이다.

## 3. 좌석 상태

```
AVAILABLE ──홀드──▶ HELD ──예매 요청──▶ HELD(결제 대기 예매 있음) ──성공 콜백(만료 전)──▶ SOLD
                     │                         │
                     │                         └─ 실패 콜백 ─▶ HELD 그대로(예매만 실패)
                     └─ 5분 경과(만료) ─▶ 다시 홀드 가능
```

| 현재 상태 | 홀드 요청 | 예매(확정) 요청 |
|---|---|---|
| AVAILABLE | 성공 → HELD | 홀드가 없다: 404 `NOT_FOUND` (Q4) |
| HELD, 만료 전 | 다른 사용자: 409 `SEAT_ALREADY_HELD`. 본인: 409 `SEAT_ALREADY_HELD`, 만료 시각은 늘지 않는다 (Q2) | 홀드한 본인: 결제 대기 예매 생성(좌석은 HELD 그대로). 다른 사용자: 403 `FORBIDDEN` (Q3) |
| HELD, 만료됨 | 성공 → HELD(새 홀드) | 409 `HOLD_EXPIRED` |
| SOLD | 409 `SEAT_ALREADY_SOLD` | 다른 사용자: 409 `SEAT_ALREADY_SOLD`. 그 좌석을 산 본인의 같은 홀드: 같은 예매를 돌려준다 (Q1·Q13) |

### 예매 상태

| 상태 | 뜻 | 좌석 |
|---|---|---|
| `PENDING` | 결제 대기. 결제사 콜백을 기다린다 | HELD 그대로(홀드 만료 시각도 그대로) |
| `PAID` | 성공 콜백이 홀드 만료 전에 와서 팔림 | SOLD |
| `FAILED` | 실패 콜백. 예매만 실패하고 홀드는 남는다. 홀드가 만료 전이면 새 예매 요청을 할 수 있다 | HELD 그대로 |
| `REFUND_REQUIRED` | 성공 콜백이 왔지만 팔 수 없었다(홀드 만료, 다른 홀드로 대체, 이미 팔림). 돈은 받았으니 환불이 필요하다고 기록만 한다 | 바꾸지 않는다 |

- `PAID`, `FAILED`, `REFUND_REQUIRED`는 끝난 상태다. 끝난 예매에 콜백이 또 오면(같은 결과든 다른 결과든) 아무것도 바꾸지 않고 지금 상태를 돌려준다.
- 성공 콜백을 처리할 때 만료 판단은 **콜백을 처리하는 순간의 서버 시각**으로 한다. 예매 요청 시각이 아니다.
- 예매 요청에는 `Idempotency-Key` 헤더(1~255자)가 필요하다. 키는 사용자별로 따로 본다: 다른 사용자가 같은 키를 써도 서로의 예매와 섞이지 않는다. 같은 사용자가 같은 키로 다시 보내면 같은 예매(같은 `booking_id`)를 돌려준다. 같은 키를 다른 홀드에 쓰면 409 `IDEMPOTENCY_KEY_REUSED`.
- 같은 홀드에 결제 대기·결제 완료 예매가 이미 있으면, 홀드한 본인이 다른 키로 다시 요청해도 새 예매를 만들지 않고 그 예매를 돌려준다 (Q1·Q13). 마지막 예매가 `FAILED`이고 홀드가 만료 전이면 새 키로 새 예매를 만든다.

- 홀드 유지 시간: **5분(300초)**.
- 만료 판정: 홀드 시각이 `T`이면 `expires_at = T + 300초`이고, **현재 시각 ≥ `expires_at`이면 만료**다. 예: 10:00:00에 잡은 홀드는 10:04:59까지 유효하고 10:05:00부터 만료다.
- **예매 요청은 그 좌석을 홀드한 사용자가, 그 홀드가 만료되기 전에만 할 수 있다.** 좌석이 SOLD가 되는 것은 성공 콜백이 홀드 만료 전에 처리될 때뿐이다.
- SOLD는 어떤 경우에도 다시 HELD나 AVAILABLE이 되지 않는다.
- **좌석맵 표시:** 만료된 HELD는 좌석맵에 `AVAILABLE`로 보인다(결제 대기 예매가 있어도 같다). 만료 전 HELD는 `HELD`, SOLD는 `SOLD`로 보인다.

## 4. 사용자 구분
- 로그인은 없다. 모의 사용자 헤더 `X-User-Id`로 사용자를 구분한다.
- **공연 목록과 좌석맵 조회는 `X-User-Id` 없이 된다.** 헤더가 있어도 결과는 같다.
- **홀드와 확정만 `X-User-Id`가 필요하다.** 헤더가 없으면 **401 `UNAUTHORIZED`** 를 반환한다.
- `X-User-Id` 값은 1~255자다. 공백뿐이거나 255자를 넘으면 헤더가 없는 것과 같이 401 `UNAUTHORIZED`다(Q10 일부).
- **결제 콜백은 모의 결제사가 보내므로 `X-User-Id`가 없다.** 실제 결제사 서명 검증은 이번 범위 밖이다.

## 5. 오류 응답
- 모든 오류 응답 본문은 정확히 두 칸이다.
  ```json
  { "code": "SEAT_ALREADY_HELD", "message": "사람이 읽을 설명" }
  ```
- `code`는 아래 표의 고정 문자열이다. `message`는 사람이 읽는 설명이며, 테스트는 문자열 내용이 아니라 존재 여부와 타입(문자열)만 확인한다.
- 상태와 부딪히는 요청은 409다.

| HTTP | code | 언제 |
|---|---|---|
| 400 | `VALIDATION_ERROR` | 요청 형식 오류: 예매 요청에 `Idempotency-Key` 없음·공백뿐·255자 초과, 콜백 본문의 `result`가 없거나 `SUCCEEDED`·`FAILED`가 아님 |
| 401 | `UNAUTHORIZED` | 홀드·확정 요청에 `X-User-Id` 헤더 없음, 공백뿐, 255자 초과 |
| 403 | `FORBIDDEN` | 다른 사용자의 홀드로 확정하려 함 (Q3) |
| 404 | `NOT_FOUND` | 없는 공연, 없는 좌석 (lead 제안, Q9), 없는 홀드 (Q4), 없는 예매(콜백) |
| 409 | `SEAT_ALREADY_HELD` | 홀드가 만료 전인 좌석을 홀드하려 함(본인 홀드 포함, Q2) |
| 409 | `SEAT_ALREADY_SOLD` | SOLD 좌석을 홀드하거나, 남이 산 좌석을 확정하려 함 |
| 409 | `HOLD_EXPIRED` | 만료된 홀드로 확정하려 함 |
| 409 | `IDEMPOTENCY_KEY_REUSED` | 같은 사용자가 같은 `Idempotency-Key`를 다른 홀드에 씀 |
| 500 | `INTERNAL_ERROR` | 서버가 처리하지 못한 오류(예: DB 연결 끊김). `message`에 내부 정보(예외 이름, DB 주소·비밀번호)를 넣지 않는다 (#17 지적 A) |

## 6. 데이터와 스택
- **스택:** Python, FastAPI, PostgreSQL.
- **공연과 좌석은 시드 데이터로 준비한다.** 공연·좌석 등록 API는 만들지 않는다.

## 7. 테스트 가능성 요구사항
- 5분 만료를 실제로 5분 기다리지 않고 검증할 수 있도록, 서버는 **현재 시각을 테스트에서 주입·조작할 수 있는 방법**을 제공해야 한다. 구체적인 방식은 API 계약/설계 단계에서 정한다.
- 동시성 원칙은 실제로 동시에 요청을 보내는 테스트로 검증한다(예: 같은 좌석에 동시 홀드 10건).
- 테스트마다 아래 공통 예시 데이터(또는 그 일부)로 시드를 다시 넣을 수 있어야 한다. 방법은 API 계약/설계 단계에서 정한다.

## 8. 이번에 빼는 것
- 화면(UI). 나중에 API 계약 파일로 타입을 만들어 붙인다.
- 실제 결제(PG 연동). 모의 결제만 한다. 결제사 서명 검증도 하지 않는다.
- 실제 환불 요청. `REFUND_REQUIRED`로 기록만 한다.
- 대사(오래 남은 결제 대기 예매를 결제사에 조회해 맞추기).
- 여러 좌석 한꺼번에 홀드·예매.
- 대기열.
- 관리자 화면.
- 공연·좌석 등록 API.
- **API 계약 파일**은 이 문서 단계에서 쓰지 않는다. 엔드포인트 경로, 요청·응답 필드 이름, 성공 상태 코드(200/201 등)는 API 계약에서 정한다.

## 10. 결정 사항
열린 질문에서 결정으로 옮긴 것이다.

| 원래 질문 | 결정 |
|---|---|
| (4절) 조회에도 헤더가 필요한가 | 공연 목록·좌석맵 조회는 헤더 없이 된다. 홀드·확정만 헤더가 필요하고 없으면 401 `UNAUTHORIZED`. |
| Q1·Q13 | 이미 예매를 만든 홀드로 같은 사람이 다시 요청하면(동시 요청 포함) 같은 예매를 돌려준다. 예매 리소스는 `booking_id`와 예매 상태를 가진다. 같은 사용자의 동시 홀드는 Q2에 따라 1건 성공, 나머지 409 `SEAT_ALREADY_HELD`. |
| Q2 | 본인이 이미 잡은 좌석을 만료 전에 다시 홀드하면 409 `SEAT_ALREADY_HELD`이고 만료 시각은 늘리지 않는다. |
| Q3 | 다른 사용자의 홀드로 확정하면 403 `FORBIDDEN`. |
| Q4 | 홀드 없이 확정(없는 `hold_id`)하면 404 `NOT_FOUND`. |
| Q10 일부 | `X-User-Id`는 1~255자. 공백뿐이거나 255자를 넘으면 401 `UNAUTHORIZED`. 허용 문자 규칙은 Q10에 남는다. |
| Q11 | 모의 결제는 성공과 실패를 둘 다 흉내 낸다(콜백 `result`). 실패하면 예매만 `FAILED`, 홀드는 남는다. |
| Q7 일부 | 좌석맵에서 만료된 HELD는 `AVAILABLE`로 보인다. 홀더·만료 시각 노출 여부는 Q7에 남는다. |
| Q8 | 공연과 좌석은 시드 데이터로 준비한다. 등록 API는 만들지 않는다. |
| Q12 일부 | 스택은 Python FastAPI + PostgreSQL. 동시성 제어 방식은 Q12에 남는다. |
| Q15 | 과부하로 DB 연결 대기(`pool_timeout`)를 넘기면 지금처럼 500 `INTERNAL_ERROR`. 별도 503 응답·`Retry-After`는 두지 않는다. |

## 11. 열린 질문
아래는 정해지지 않았다. 답이 나오기 전에는 관련 인수 조건을 테스트로 옮기지 않는다(스토리에 `[열린 질문 Qn]`으로 표시).

- **Q5. 사용자 한 명이 여러 좌석을 각각 홀드할 수 있는가?** "여러 좌석 한꺼번에"는 범위 밖이지만, 한 건씩 여러 번 잡는 것을 막을지 정해지지 않았다.
- **Q6. 홀드 취소(사용자가 직접 놓기)** 가 이번 범위에 있는가?
- **Q7. 좌석맵에 홀드한 사람·만료 시각을 노출하는가?** (만료된 HELD를 `AVAILABLE`로 보이는 것은 결정됐다.)
- **Q9. 404와 400.** 없는 공연·좌석에 404 `NOT_FOUND`를 쓰는 것은 lead 제안이다. 요청 형식 오류(필수 값 누락 등)에 400과 별도 `code`가 필요한가? (6장에서 `Idempotency-Key` 없음과 콜백 본문 오류만 400 `VALIDATION_ERROR`로 정했다. 그 밖의 형식 오류는 아직 열려 있다.)
- **Q10. `X-User-Id` 값 규칙.** (길이 1~255자와 공백뿐·초과 시 401은 결정됐다.) 허용 문자 규칙이 있는가?
- **Q12. 동시성 제어 방식.** (스택은 결정됐다.) PostgreSQL에서 행 잠금, 조건부 UPDATE, 유일 제약 중 무엇으로 "SOLD 한 번"을 보장하는가?
- **Q14. 테스트용 PostgreSQL을 어떻게 준비하는가?** (스택 결정으로 새로 생긴 질문) 로컬 설치, Docker, 테스트용 임시 DB 중 무엇으로 누구나 같은 환경을 만드는가?

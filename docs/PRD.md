# PRD — 콘서트 좌석 예매 1차 범위(MVP)

## 1. 목표
사용자가 다음 흐름을 API로 끝까지 진행할 수 있다.

1. 공연 목록을 본다.
2. 공연 하나의 좌석맵(좌석별 상태)을 본다.
3. 좌석 하나를 5분 동안 잡는다(홀드).
4. 모의 결제로 예매를 확정한다.

## 2. 핵심 원칙
- **좌석 하나는 한 번만 팔린다.** 같은 요청이 동시에 여러 번 와도 마찬가지다.
- 좌석에 대한 홀드와 확정은 동시에 들어와도 위 원칙을 깨지 않아야 한다. 이것이 이번 범위에서 가장 중요한 검증 대상이다.

## 3. 좌석 상태

```
AVAILABLE ──홀드──▶ HELD ──모의 결제 확정──▶ SOLD
                     │
                     └─ 5분 경과(만료) ─▶ 다시 홀드 가능
```

| 현재 상태 | 홀드 요청 | 확정 요청 |
|---|---|---|
| AVAILABLE | 성공 → HELD | 거절(코드는 Q4) |
| HELD, 만료 전 | 거절 409 `SEAT_ALREADY_HELD` | 홀드한 본인만 성공 → SOLD. 다른 사용자는 거절(코드는 Q3) |
| HELD, 만료됨 | 성공 → HELD(새 홀드) | 거절 409 `HOLD_EXPIRED` |
| SOLD | 거절 409 `SEAT_ALREADY_SOLD` | 거절 409 `SEAT_ALREADY_SOLD` |

- 홀드 유지 시간: **5분(300초)**.
- 만료 판정: 홀드 시각이 `T`이면 `expires_at = T + 300초`이고, **현재 시각 ≥ `expires_at`이면 만료**다. 예: 10:00:00에 잡은 홀드는 10:04:59까지 유효하고 10:05:00부터 만료다.
- **예매 확정은 그 좌석을 홀드한 사용자가, 그 홀드가 만료되기 전에만 할 수 있다.**
- SOLD는 어떤 경우에도 다시 HELD나 AVAILABLE이 되지 않는다.
- **좌석맵 표시:** 만료된 HELD는 좌석맵에 `AVAILABLE`로 보인다. 만료 전 HELD는 `HELD`, SOLD는 `SOLD`로 보인다.

## 4. 사용자 구분
- 로그인은 없다. 모의 사용자 헤더 `X-User-Id`로 사용자를 구분한다.
- **공연 목록과 좌석맵 조회는 `X-User-Id` 없이 된다.** 헤더가 있어도 결과는 같다.
- **홀드와 확정만 `X-User-Id`가 필요하다.** 헤더가 없으면 **401 `UNAUTHORIZED`** 를 반환한다.

## 5. 오류 응답
- 모든 오류 응답 본문은 정확히 두 칸이다.
  ```json
  { "code": "SEAT_ALREADY_HELD", "message": "사람이 읽을 설명" }
  ```
- `code`는 아래 표의 고정 문자열이다. `message`는 사람이 읽는 설명이며, 테스트는 문자열 내용이 아니라 존재 여부와 타입(문자열)만 확인한다.
- 상태와 부딪히는 요청은 409다.

| HTTP | code | 언제 |
|---|---|---|
| 401 | `UNAUTHORIZED` | 홀드·확정 요청에 `X-User-Id` 헤더 없음 |
| 404 | `NOT_FOUND` | 없는 공연 또는 없는 좌석 (lead 제안, Q9) |
| 409 | `SEAT_ALREADY_HELD` | 다른 홀드가 만료 전인 좌석을 홀드하려 함 |
| 409 | `SEAT_ALREADY_SOLD` | SOLD 좌석을 홀드하거나 확정하려 함 |
| 409 | `HOLD_EXPIRED` | 만료된 홀드로 확정하려 함 |

## 6. 데이터와 스택
- **스택:** Python, FastAPI, PostgreSQL.
- **공연과 좌석은 시드 데이터로 준비한다.** 공연·좌석 등록 API는 만들지 않는다.

## 7. 테스트 가능성 요구사항
- 5분 만료를 실제로 5분 기다리지 않고 검증할 수 있도록, 서버는 **현재 시각을 테스트에서 주입·조작할 수 있는 방법**을 제공해야 한다. 구체적인 방식은 API 계약/설계 단계에서 정한다.
- 동시성 원칙은 실제로 동시에 요청을 보내는 테스트로 검증한다(예: 같은 좌석에 동시 홀드 10건).
- 테스트마다 아래 공통 예시 데이터(또는 그 일부)로 시드를 다시 넣을 수 있어야 한다. 방법은 API 계약/설계 단계에서 정한다.

## 8. 이번에 빼는 것
- 화면(UI). 나중에 API 계약 파일로 타입을 만들어 붙인다.
- 실제 결제(PG 연동). 모의 결제만 한다.
- 여러 좌석 한꺼번에 홀드·예매.
- 대기열.
- 관리자 화면.
- 공연·좌석 등록 API.
- **API 계약 파일**은 이 문서 단계에서 쓰지 않는다. 엔드포인트 경로, 요청·응답 필드 이름, 성공 상태 코드(200/201 등)는 API 계약에서 정한다.

## 10. 결정 사항
열린 질문에서 결정으로 옮긴 것이다.

| 원래 질문 | 결정 |
|---|---|
| (4절) 조회에도 헤더가 필요한가 | 공연 목록·좌석맵 조회는 헤더 없이 된다. 홀드·확정만 헤더가 필요하고 없으면 401 `UNAUTHORIZED`. |
| Q3 일부 | 다른 사용자의 홀드로는 확정할 수 없다(거절). 상태 코드와 `code`는 Q3에 남는다. |
| Q4 일부 | 홀드 없이는 확정할 수 없다(거절). 상태 코드와 `code`는 Q4에 남는다. |
| Q7 일부 | 좌석맵에서 만료된 HELD는 `AVAILABLE`로 보인다. 홀더·만료 시각 노출 여부는 Q7에 남는다. |
| Q8 | 공연과 좌석은 시드 데이터로 준비한다. 등록 API는 만들지 않는다. |
| Q12 일부 | 스택은 Python FastAPI + PostgreSQL. 동시성 제어 방식은 Q12에 남는다. |

## 11. 열린 질문
아래는 정해지지 않았다. 답이 나오기 전에는 관련 인수 조건을 테스트로 옮기지 않는다(스토리에 `[열린 질문 Qn]`으로 표시).

- **Q1. 같은 사용자의 중복·동시 요청.** 같은 사용자가 같은 좌석에 홀드를 동시에 여러 번 보내면, 성공 1건 + 나머지 409인가, 아니면 모두 같은 홀드를 돌려받는가(멱등)? 확정 요청이 같은 사용자로 동시에 여러 번 오면 어떻게 응답하는가? (어느 쪽이든 "SOLD는 한 번"은 지킨다.)
- **Q2. 본인이 이미 잡은 좌석을 다시 홀드하면?** 409 `SEAT_ALREADY_HELD`인가, 기존 홀드를 그대로 반환하는가, 만료 시각을 연장하는가?
- **Q3. 다른 사람의 홀드로 확정하려 할 때의 응답.** 거절은 결정됐다. 403인가 409인가, `code`는 무엇인가?
- **Q4. 홀드 없이(AVAILABLE 좌석에) 확정하려 할 때의 응답.** 거절은 결정됐다. 상태 코드와 `code`는?
- **Q5. 사용자 한 명이 여러 좌석을 각각 홀드할 수 있는가?** "여러 좌석 한꺼번에"는 범위 밖이지만, 한 건씩 여러 번 잡는 것을 막을지 정해지지 않았다.
- **Q6. 홀드 취소(사용자가 직접 놓기)** 가 이번 범위에 있는가?
- **Q7. 좌석맵에 홀드한 사람·만료 시각을 노출하는가?** (만료된 HELD를 `AVAILABLE`로 보이는 것은 결정됐다.)
- **Q9. 404와 400.** 없는 공연·좌석에 404 `NOT_FOUND`를 쓰는 것은 lead 제안이다. 요청 형식 오류(필수 값 누락 등)에 400과 별도 `code`가 필요한가?
- **Q10. `X-User-Id` 값 규칙.** 빈 문자열(`X-User-Id: `)도 "헤더 없음"으로 보고 401인가? 허용 형식(길이, 문자)이 있는가?
- **Q11. 모의 결제 실패.** 모의 결제는 항상 성공하는가, 실패를 흉내 내는 방법이 필요한가? 실패하면 홀드는 유지되는가?
- **Q12. 동시성 제어 방식.** (스택은 결정됐다.) PostgreSQL에서 행 잠금, 조건부 UPDATE, 유일 제약 중 무엇으로 "SOLD 한 번"을 보장하는가?
- **Q13. 확정 결과로 무엇을 돌려주는가?** 예매 번호 등 예매 리소스가 필요한가, 좌석 상태만 바뀌면 되는가?
- **Q14. 테스트용 PostgreSQL을 어떻게 준비하는가?** (스택 결정으로 새로 생긴 질문) 로컬 설치, Docker, 테스트용 임시 DB 중 무엇으로 누구나 같은 환경을 만드는가?

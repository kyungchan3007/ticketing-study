# 트래픽 계산 시트

오픈 직후 트래픽을 단계별로 나눠 초당 요청 수를 계산한다. 계산은 `scripts/capacity.py`가 하고(`uv run python scripts/capacity.py`), 이 문서의 공식을 그대로 따른다.
`[가정]`은 실측이나 결정으로 바뀔 수 있는 값이다. `[실측 필요]`는 아직 모르는 값이다.

## 1. 입력값

| 기호 | 값 | 뜻 | 구분 |
|---|---|---|---|
| `S` | 50,000 | 좌석 수 | [가정] |
| `U` | 1,000,000 | 오픈 뒤 접속하는 사람 수 | [가정] |
| `A` | 60초 | `U`명이 접속하는 시간(오픈 1분) | [가정] |
| `P` | 5초 | 대기 중 순번 확인(폴링) 간격 | [가정] |
| `R` | 200명/초 | 대기열에서 입장시키는 속도 | [가정] |
| `v` | 2회 | 입장한 사람 1명의 좌석 조회 횟수 | [가정] |
| `h` | 2회 | 입장한 사람 1명의 홀드 횟수 | [가정] |
| `p` | 0.4 (40%) | 입장한 사람 중 결제하는 비율 | [가정] |
| `k` | 1회 | 결제하는 사람 1명의 결제 횟수 | [가정] |

## 2. lead가 새로 정한 가정

입력값만으로는 계산이 정해지지 않아 lead가 정한 것이다. 이유는 `docs/decisions.md`에 있다.

| 번호 | 가정 | 구분 |
|---|---|---|
| G1 | 접속은 오픈 뒤 `A`초 동안 고르게 들어온다. 접속 속도 = `U / A`. | [가정] |
| G2 | 한 사람은 대기열에 한 번만 진입한다(진입 요청 1건). | [가정] |
| G3 | 대기 중인 사람은 모두 정확히 `P`초마다 순번을 확인한다. 입장하면 폴링을 멈춘다. **확인 시점은 사람마다 고르게 퍼져 있다**(모두가 같은 순간에 확인하지 않는다). 그래서 폴링 초당 요청 = 그 순간 대기 인원 / `P`. | [가정] |
| G4 | 입장은 오픈 순간(t=0)부터 일정하게 초당 `R`명이다. | [가정] |
| G5 | 결제 1건은 좌석 1석을 판다. 결제 실패, 홀드 만료로 다시 풀린 좌석은 세지 않는다. | [가정] |
| G6 | **매진되면 입장을 멈춘다.** 매진 시점은 결제 수가 좌석 수와 같아질 때이고, 그때 남은 대기자 `U − N`명은 매진 뒤 `P`초 안에 한 번 더 확인해 매진 안내를 받고 폴링을 멈춘다. 이 매진 안내 응답 `U − N`건을 폴링 총량에 더한다. | [가정] |
| G7 | 입장한 사람은 입장한 직후 좌석 조회·홀드·결제를 한다. 그래서 이 요청들은 입장 기간 동안 고르게 퍼진다. | [가정] |
| G8 | 대기열 진입과 폴링은 PostgreSQL을 쓰지 않는다(대기열 저장소는 별도). DB 작업은 좌석 조회 1회 = 읽기 1건, 홀드 1회 = 쓰기 트랜잭션 1건, 결제 1회 = 쓰기 트랜잭션 1건이다. | [가정] |

## 3. 공식

### 3.1 입장 인원과 기간
- 입장 인원 `N = min(U, S / (p × k))` — 결제 수 `N × p × k`가 좌석 수 `S`에 닿으면 매진(G5, G6).
- 입장 기간 `T = N / R` (초).
- 아래 공식은 `U / A > R`(접속이 입장보다 빠름)이고 `T ≥ A`(접속이 끝난 뒤에 매진)일 때만 쓴다. 아니면 계산하지 않고 오류로 알린다.

### 3.2 행별 공식
`평균 초당 = 요청 수 / 기간`. `최대 초당`은 그 기간 안에서 가장 큰 순간값이다.

| 행 | 사람 수 | 요청 수 | 기간(초) | 평균 초당 | 최대 초당 |
|---|---|---|---|---|---|
| 대기열 진입 | `U` | `U` | `A` | `U / A` | `U / A` |
| 순번 확인(폴링) | `U` | `Wsum / P + (U − N)` | `T + Pn` | `(Wsum / P + (U − N)) / (T + Pn)` | `(U − R × A) / P` |
| 좌석 조회 | `N` | `N × v` | `T` | `R × v` | `R × v` |
| 홀드 | `N` | `N × h` | `T` | `R × h` | `R × h` |
| 모의 결제 | `N × p` | `N × p × k` | `T` | `R × p × k` | `R × p × k` |
| DB 작업 | `N` | `N × (v + h + p × k)` | `T` | `R × (v + h + p × k)` | `R × (v + h + p × k)` |
| API 합계(최대가 겹치는 순간) | `U` | 위 다섯 API 행 요청 수의 합 | `T + Pn` | 요청 수 합 / (`T + Pn`) | 다섯 API 행 최대 초당의 합 |

- `Wsum`은 대기 인원을 시간으로 적분한 값(사람·초)이다. 대기 인원 `W(t)` = 접속한 사람 − 입장한 사람.
  - 0 ≤ t ≤ `A`: `W(t) = (U / A − R) × t`
  - `A` ≤ t ≤ `T`: `W(t) = U − R × t`
  - `Wsum = (U / A − R) × A² / 2 + U × (T − A) − R × (T² − A²) / 2`
- 폴링 요청 수의 `U − N`은 매진 안내 응답이다(G6). 이 응답은 매진 뒤 `P`초 안에 오므로 폴링과 API 합계의 기간은 `T + Pn`이다. `Pn`은 매진 안내 기간으로, 남은 대기자가 있으면(`U − N > 0`) `P`, 없으면(`N = U`, 모두 입장) 0이다. 매진 안내의 초당 요청은 `(U − N) / P`로, `A` ≤ t 에서 대기 인원이 줄어들기만 하므로 폴링 최대보다 크지 않다.
- 폴링 최대는 접속이 끝나는 순간(t = `A`)의 대기 인원 `U − R × A`에서 나온다.
- **주의(G3).** 폴링 최대는 확인 시점이 사람마다 고르게 퍼져 있다는 가정에서 나온 값이다. 모두가 같은 순간에 확인하면(예: 매 5초 정각) 대기 인원 `U − R × A`가 한꺼번에 요청해, 그 1초의 요청이 폴링 최대의 `P`배(기본값으로 약 5배, 약 98.8만 건/초)가 될 수 있다. 이 계산 시트는 이 경우를 계산하지 않는다.
- DB 작업 행은 G8에 따라 좌석 조회·홀드·결제만 센다. 그중 읽기는 `R × v`, 쓰기는 `R × (h + p × k)`.
- API 합계의 최대는 각 행의 최대를 더한 값이고, 이 연속 모델에서 API 초당 요청의 **상한**이다. t가 `A`보다 작은 쪽에서 `A`에 다가갈수록 진입(`U / A`), 폴링(`W(t) / P`), 예매 API(`R × (v + h + p × k)`)의 합이 이 값에 한없이 가까워지고, 어느 순간에도 이 값을 넘지 않는다.

## 4. 계산 결과

`uv run python scripts/capacity.py` 출력. (입력값과 가정이 바뀌면 다시 돌려서 바꾼다.)

입장 인원 N = 125,000명, 입장 기간 T = 625초

| 행 | 사람 수 | 요청 수 | 기간(초) | 평균 초당 | 최대 초당 |
|---|---:|---:|---:|---:|---:|
| 대기열 진입 | 1,000,000 | 1,000,000 | 60 | 16,667 | 16,667 |
| 순번 확인(폴링) | 1,000,000 | 112,062,500 | 630 | 177,877 | 197,600 |
| 좌석 조회 | 125,000 | 250,000 | 625 | 400 | 400 |
| 홀드 | 125,000 | 250,000 | 625 | 400 | 400 |
| 모의 결제 | 50,000 | 50,000 | 625 | 80 | 80 |
| DB 작업 | 125,000 | 550,000 | 625 | 880 | 880 |
| API 합계 | 1,000,000 | 113,612,500 | 630 | 180,337 | 215,147 |

DB 작업 중 읽기 400건/초, 쓰기 트랜잭션 480건/초.

가장 큰 초당 요청은 **순번 확인(폴링)** 이다. 접속이 끝나는 순간(오픈 60초) 대기 인원 약 98.8만 명이 5초마다 확인해 최대 약 19.8만 건/초가 된다. 대기열 진입(약 1.7만 건/초)과 겹치면 API 합계 최대는 약 21.5만 건/초다. 단, 확인 시점이 사람마다 고르게 퍼져 있다는 가정(G3)에서 나온 값이고, 모두가 같은 순간에 확인하면 폴링 최대가 약 5배(약 98.8만 건/초)가 될 수 있다(3.2절 주의). 예매 API(조회·홀드·결제)는 입장 속도로 묶여 합쳐도 880건/초다.
